# agent-runtime-lab

**一个零第三方依赖的 LLM Agent 运行时**：把「任务规划 → 工具调用 → 观察 → 自我修正」这条主循环、
记忆管理、RAG、多智能体协作与效果评测**从零实现一遍**，并且让整条链路在**没有 API Key、
没有网络**的 CI 里可复现地跑完。

> ⚠️ **先说清楚这是什么**
> 本项目是**个人自建的工程实践项目**，不是任何商业 Agent 框架的替代品，
> 也没有在生产环境上线过。它的目标是把 Agent 运行时里那些**确定性的工程部分**
> （function calling 协议、参数校验、失败回填、上下文压缩、记忆检索、评测口径）
> 做扎实、做可测 —— 模型本身通过可插拔后端接入，
> 测试与评测使用**脚本化后端**产生确定性流量，所以指标可复现、缺陷可归因。
> 不做什么、边界在哪，见文末[「边界与已知限制」](#边界与已知限制)。

---

## 为什么做这个

商用 Agent 框架把「模型调用」和「运行时」揉在一起，出问题时很难分清是模型的问题还是框架的问题。
本项目的取舍是**把运行时做成一个不依赖模型、不依赖网络的纯 Python 库**：

- 在**没有 API Key 的 CI** 里也能跑完整回归 —— 因为模型被抽象成 `LLMBackend`，
  测试用 `ScriptedBackend`（按脚本返回确定性的工具调用），评测用同一套后端产流量；
- 换成真实模型时**代码不用改**：`OpenAICompatBackend` 用标准库 `urllib` 直接对接
  OpenAI 兼容的 `/chat/completions`（DeepSeek / vLLM / Ollama 均可），
  消息格式完全按 function calling 协议对齐；
- 于是「运行时 / 工具层 / 记忆 / 自我修正」这些**确定性组件**的缺陷可以被稳定复现，
  而不是淹没在模型的随机性里。

## 快速开始

```bash
# 零依赖：只用 Python 标准库（3.8 起）
python -m agentlab tools                       # 打印工具清单与自动生成的 JSON Schema
python -m agentlab run "查一下 cnc-03 的温度指标"  # 跑一个任务并打印 trace
python -m agentlab eval --out reports          # 跑 14 任务评测集，产出 JSON + Markdown 报告
python -m agentlab demo                        # 多智能体协作演示（Supervisor + 3 个 Worker）

python -m pytest tests -q                      # 204 个单元测试
```

接入真实模型（可选）：

```bash
export AGENTLAB_API_KEY=sk-xxx
export AGENTLAB_BASE_URL=https://api.deepseek.com/v1
python -c "
from agentlab import AgentRuntime, OpenAICompatBackend, default_registry
agent = AgentRuntime(OpenAICompatBackend(model='deepseek-chat'), default_registry())
print(agent.run('用计算器算 (85-68.4)/85*100').answer)
"
```

## 架构

```
agentlab/
├── llm.py          模型后端：ScriptedBackend（确定性）/ RuleBasedBackend（规则）/ OpenAICompatBackend（真实）
├── tools.py        JSON Schema 自动生成 · 执行前参数校验 · Function Calling 协议 · 沙箱文件工具 · AST 安全计算器
├── memory.py       短期缓冲（token 预算 + 摘要压缩）· 长期向量记忆（hashing trick）· 工作记忆（带溯源）
├── rag.py          切块 · 检索 · 引用溯源 · RAG-as-a-tool
├── planner.py      ReAct 单步提示词 · Plan-and-Execute 计划生成/解析/合并
├── runtime.py      ★ 主循环：规划 → 工具调用 → 观察 → 自我修正 → 终止；上下文压缩
├── orchestrator.py Supervisor + Worker + 消息总线（任务拆分、按技能选人、失败改派、汇总）
├── trace.py        结构化 trace（每一步的 phase / 耗时 / 工具 / 错误）
└── eval.py         评测任务集 · 判据 · 指标 · JSON/Markdown 报告
```

数据流（一次 `AgentRuntime.run`）：

```
task ─┬─▶ [RAG 前置检索] ──▶ 系统提示词（工具表 + 计划 + 工作记忆 + 检索片段）
      │
      └─▶ 循环（max_steps 上限）
            ① 上下文预算治理（按"消息组"压缩，保证 tool 与 assistant.tool_calls 成对）
            ② backend.chat(messages, tools)         ← 唯一与模型耦合的地方
            ③ 有 tool_calls？ → 参数校验 → 执行 → 观察结果回填（tool 角色消息）
            ④ 无 tool_calls？ → 最终回答，收敛
            ⑤ 每一步都写 trace；失败走四条自我修正路径之一
```

## 关键实现点

### 1. 工具参数在执行前就被校验

JSON Schema 从**函数签名 + docstring**自动生成，约束（枚举 / 取值范围 / 元素个数）通过
`constraints=` 补充；模型给的参数先过 `validate_arguments`，不合法**根本不会执行工具**，
而是把**字段级错误 + 正确签名**回填给模型：

```
参数校验失败，工具未执行。
错误: 参数 'window_min' 小于最小值 1
正确签名: query_metric(device:string, metric:string, window_min?:integer)
```

> 这里踩过一个**静默失效**的坑：模块里写了 `from __future__ import annotations`（PEP 563）之后，
> 注解在运行期是**字符串**，`inspect.signature()` 拿到的是 `'int'` 而不是 `int`，
> 直接映射会生成**没有 `type` 字段的空 schema** ——
> 校验永远通过、错误参数永远拦不住，而且不报错。
> 修法是统一用 `get_type_hints` 求值，并在失败时退化为「逐参数在 typing 命名空间里求值」。
> 回归测试：`tests/test_tools.py::test_typed_annotations_survive_postponed_evaluation`。

### 2. 四条自我修正路径（都有测试与评测用例）

| 失败形态 | 运行时的处理 | 评测里的用例 | 实测触发 |
|---|---|---|---|
| 参数非法（类型/范围/枚举） | 执行前拦截 → 回填字段级错误与正确签名 | `invalid-arguments-recovery` | 1 次 |
| 工具名不存在 | 回填**候选工具建议**（difflib 近似匹配） | `unknown-tool-recovery` | 1 次 |
| 工具内部报错（超时等） | 错误结构化 → 回填观察结果 → 允许重试 | `tool-error-retry` | 恢复成功 |
| 原地打转 | 同签名的**第 3 次成功调用**被拦截并回填提示 | `loop-guard` | 2 次 |
| 计划中的某步失败 | **保留已完成步骤**，只重写剩余路径（重规划） | `plan-and-replan` | 1 次 |

> 打转判据刻意只看**成功的**重复调用：工具报错后的重试是有意义的修正，
> 早期实现按"调用次数"计数，结果把「失败两次后终于成功」的合法重试也拦掉了
> （见 `tests/test_runtime.py::test_tool_error_is_reported_and_recoverable`）。

### 3. 上下文压缩按「消息组」进行

token 预算超限时不是简单地丢最旧的消息 —— `assistant(tool_calls)` 与它后面所有的
`tool` 消息必须**同生共死**，否则函数调用协议不再成对，真实模型会直接报错。
短期记忆在没有 `summarizer` 时也**不会静默丢历史**，而是退化成截断摘要。

### 4. 记忆分三层，事实带溯源

- **短期**：token 预算 + 摘要压缩（摘要自身也有限幅，避免膨胀从 turns 搬到 summary）；
- **长期**：hashing trick + 字符 bi-gram 的向量记忆，可持久化 JSON，
  检索不依赖任何第三方向量库；
- **工作记忆**：工具返回值以 `来源: tool:query_metric / 第 2 步` 的形式入账，
  提示词里会带上出处 —— 模型编造数字时，trace 里能看出来。

中文检索的两个实测结论（都固化成了回归测试）：

| 现象 | 测量 | 决策 |
|---|---|---|
| 短查询把**无关文档排到第一位**，甚至出现负相似度 | `dim=256`：4 条查询里有 1 条排错；`dim>=512`：4/4 正确且稳定 | 默认维度取 **512** |
| 「温度异常」与「振动异常」互相串味 | 只靠单字时，共用的「异」「常」权重过高 | 单字权重 **0.3**、bi-gram 权重 1.0 |

### 5. 多智能体：拆分 → 选人 → 失败改派 → 如实汇总

`Supervisor` 把任务拆成子任务，按**技能标签 + 可用工具**给子任务选 Worker；
子任务失败时改派给次优 Worker；全部失败才判该子任务失败，汇总时**明确写出哪个子任务没完成**。

这里有一条容易忽略的验收判据：**运行时的 `success` 只表示"干净地收敛到了回答"，
不表示回答有依据**。一个 Worker 的所有工具都失败了、模型仍然"基于常识"给出一段回答时，
运行时判成功而子任务其实什么也没查到 —— 所以 `Worker.accepts()` 追加了
「调过工具却一次都没成功 → 不算完成」。

### 6. 评测体系：判据、指标、报告

- **任务集**：14 个任务，期望工具 / 期望答案要点 / 步数上限 / 禁用工具**人工写死**，
  不是把实际输出抄回来当期望；
- **判据**：逐项给出通过与否（收敛 / 答案要点 / 必需工具 / 未用禁用工具 / 未超步数 /
  工具序列严格匹配 / 发生重规划 / 触发上下文压缩），报告里能看到**为什么挂**；
- **指标**分四组：任务完成、工具使用、自我修正、成本；
- **报告**：JSON（可入 CI 基线比对）+ Markdown（可直接贴进复盘文档）。

## 实测结果

> 环境：**Python 3.8.0 / Windows**（本地开发与验证）；CI 另跑 3.9 与 3.12。
> **脚本化模型后端**（无网络、无 API Key）。
> 数字全部来自本仓库 `python -m agentlab eval --out reports` 的真实输出。

**单元测试：204 个全部通过**（12 个源码模块 / 约 4,150 行；8 个测试文件 / 约 2,280 行）。

**评测集（14 任务）：**

| 指标 | 数值 |
|---|---:|
| 任务成功率 | **14/14 = 1.0** |
| 工具召回率 / 准确率 | **1.0 / 1.0** |
| 平均步数 / 最大步数 | 2.79 / 5 |
| 工具调用总数 / 冗余调用 | 23 / 5 |
| 自我修正恢复率 | **1.0**（4 个任务出过错，全部最终通过） |
| 参数校验纠正 / 未知工具纠正 / 死循环拦截 | 1 / 1 / 2 |
| 触发重规划的任务 | 1 |

**确定性验证**：同一套任务连跑 3 次，除耗时类指标外的全部指标**逐字一致**。

> 评测用例之间必须完全隔离：`flaky_gateway` 这类"第一次调用必失败"的状态型工具
> 曾被整轮评测共享，先跑的用例把这次失败用掉之后，后面依赖它的用例就**静默走了另一条路径**
> ——指标随用例顺序变化。现在工具集与知识库**每个任务重建一次**，
> 并有 `test_suite_tasks_are_isolated_from_each_other` 守住这一点。

## 开发过程中被测试抓出来的真问题

这些都不是"写错了改一下"，而是**不跑测试就不会发现**的类型（也是这个项目最值得讲的部分）：

1. **PEP 563 让参数校验静默失效** —— 空 schema，校验永远通过（上文 §1）；
2. **打转判据按调用次数计数**，把"失败两次后成功"的合法重试也拦掉了（上文 §2）；
3. **哈希维度 256 导致中文短查询排序翻转**，甚至出现负相似度（上文 §4）；
4. **`ShortTermMemory.add()` 在无 summarizer 时直接丢历史** —— 与"先摘要再淘汰"的设计相矛盾，
   等于把信息静默丢掉；
5. **`VectorMemory.load()` 没有恢复自增序号** —— 载入后新增的条目会与既有 ID 冲突；
6. **评测任务之间共享状态型工具**，指标随用例顺序变化（上文「实测结果」）；
7. **Worker 把"工具全失败但答了一段话"判成成功**，多智能体的失败改派路径形同虚设（上文 §5）；
8. `WorkingMemory.set` 不限幅 —— 一个结构化的大返回值就能把提示词预算吃光；
9. 中文任务拆分按字符数过滤，把「查温度」这种 3 字真任务整段丢掉。

## 边界与已知限制

**做过的**：Agent 主循环、function calling 协议编解码、JSON Schema 生成与执行前校验、
四条自我修正路径、计划与重规划、上下文压缩、三层记忆、RAG（切块/检索/引用）、
多智能体协作与消息总线、结构化 trace、评测体系与报告、CLI。

**没做的 / 不能声称的**：

- **没有用真实大模型跑过评测**。所有指标都来自脚本化后端的确定性流量，
  衡量的是**运行时与工具链的可靠性**，不是某个模型的能力；换真实模型后任务、判据、
  指标可直接复用，但**分数会变**，本项目不给出任何"某模型任务成功率"的结论；
- **没有生产部署、没有真实用户、没有并发/高可用设计**。运行时的工具调用是**串行**的，
  没有做多工具并行、限流、重试退避策略的调优；
- **向量检索是 hashing trick，不是语义嵌入**。它靠字符 bi-gram 做词汇级相似，
  同义改写、跨语言、长文档的召回都明显弱于真实 embedding 模型；
- **`RuleBasedBackend` 是规则后端**，只用于演示与编排测试，不代表模型的规划能力；
- **文件工具只是"沙箱内的相对路径限制"**，够用于本地演示，不是安全沙箱，
  不应拿去执行不受信任的输入；
- 多智能体是**单进程串行**的 Supervisor/Worker，没有消息队列、没有分布式调度。
